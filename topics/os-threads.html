Threads

A thread is the smallest unit of CPU scheduling — a lightweight execution stream inside a process. Threads of one process share code, data and files but each has its own stack, registers and PC. Cheap to create and switch, but shared mutable state invites race conditions.

Key points

Shared vs private
Shared: text, global/heap data, open files, signals. Private per thread: stack, registers, PC, thread ID.
Benefits / risks
Benefit: low creation & switch cost, easy sharing (no IPC), true parallelism on multicore. Risk: one bad thread corrupts shared state; races without synchronization.
Models
Many-to-one (user threads, no real parallelism), one-to-one (Linux/Windows — real parallelism, kernel overhead), many-to-many (complex, rare).
Race condition
Result depends on thread interleaving on shared data (e.g. two threads doing count++). Fix with a mutex / atomics.
Concurrency ≠ parallelism
On one core, threads still help I/O-bound work (overlap waiting) but not CPU-bound work.

Diagram

Example

// The classic race: two threads each do count++ a million times
void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++)
        count++;              // read, add 1, write — NOT atomic
    return NULL;
}
// Final count is somewhere between ~1,000,000 and 2,000,000: updates are lost.
// Fix: pthread_mutex_lock/unlock around count++, or an atomic type.
Common exam traps

User-level threads: one blocking syscall blocks ALL of them, and they cannot use multiple cores. Concurrency (interleaving) is not parallelism (simultaneous execution). Java's volatile gives visibility, not atomicity — x++ still needs a lock. After fork() in a threaded program, only the calling thread exists in the child.

Practice MCQs

Q1. Threads of the same process share:

  1. stack and registers
  2. code, global/heap data, open files
  3. the program counter
  4. nothing
Show answer

Answer: B. Each thread has a private stack, registers and PC.

Q2. The main danger of threads is:

  1. they are slow
  2. shared mutable data leads to race conditions without synchronization
  3. they cannot be scheduled
  4. they need a separate PID
Show answer

Answer: B. A bug in one thread can crash the whole process.

Q3. User-level threads:

  1. are scheduled by the kernel
  2. are managed by a user library; the kernel sees one process, and one blocking call blocks all
  3. always beat kernel threads
  4. cannot share data
Show answer

Answer: B. Fast but no multicore use and no independent blocking.

Q4. A context switch between two threads of the SAME process is cheaper because:

  1. threads are smaller programs
  2. no address-space (page table / TLB) switch is needed
  3. threads have no registers
  4. it is done in hardware
Show answer

Answer: B. The MMU context and caches stay warm.

Q5. Multithreading on a single-core CPU:

  1. gives no benefit at all
  2. still helps I/O-bound programs via concurrency, but not CPU-bound ones
  3. doubles CPU speed
  4. always deadlocks
Show answer

Answer: B. Concurrency ≠ parallelism.
