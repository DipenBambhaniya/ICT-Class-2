Cloud Infrastructure, Virtualization & Pipelining

Virtualization and containerization let a data centre share physical hardware safely across many workloads; automated pipelines (CI/CD and data pipelines) turn deploying and processing that work into a repeatable, low-error process instead of manual, one-off steps.

Key points

Hypervisor (Type 1 vs Type 2)
Type 1 (bare-metal, e.g. ESXi/KVM) runs directly on hardware — used in production. Type 2 (hosted, e.g. VirtualBox) runs atop a host OS — used on desktops.
VM vs Container
A VM virtualizes hardware and runs a full guest OS (strong isolation, heavier). A container shares the host kernel and packages just the app + dependencies (lightweight, fast to start).
Orchestration (Kubernetes)
Automates deployment, scaling, networking and self-healing of many containers (Pods) across a cluster of machines (Nodes).
Infrastructure as Code
Infrastructure defined in version-controlled config files (e.g. Terraform) instead of manual clicks — reproducible, auditable, easy to rebuild.
CI/CD pipeline
Build → automated test → deploy, triggered on every code change, with strategies like blue-green, canary and rolling updates to release safely.

Diagram

Example

CI/CD pipeline for a web service, triggered on every git push:

  1. Build   -> compile code, package a container image, push to a registry
  2. Test    -> run automated unit + integration tests against the image
  3. Deploy  -> canary release: send 5% of traffic to the new version
  4. Monitor -> watch error rate/latency; if healthy, roll out to 100%
                (a rolling update); if not, roll back to the previous image

Kubernetes keeps the desired number of Pods running: if a Node hosting one
crashes, the scheduler places a replacement Pod on a healthy Node automatically
(self-healing) — no manual restart needed.
Common exam traps

Containers share the host kernel (lighter, faster, weaker isolation); VMs each run a full guest OS (heavier, stronger isolation). A Type-1 hypervisor runs on bare metal; a Type-2 hypervisor runs atop a host OS. Continuous Delivery keeps code always releasable but still needs a manual trigger — Continuous Deployment releases every passing change automatically.

Practice MCQs

Q1. A container, unlike a full virtual machine:

  1. Runs its own separate OS kernel
  2. Shares the host's OS kernel, making it lighter-weight and faster to start
  3. Cannot be moved between machines
  4. Always requires a Type-1 hypervisor
Show answer

Answer: B. This shared-kernel model is why containers start in seconds and use far fewer resources than a full VM.

Q2. A Type 1 (bare-metal) hypervisor:

  1. Runs as an application on a host OS
  2. Runs directly on physical hardware with no host OS beneath it
  3. Cannot host more than one VM
  4. Is only used for desktop virtualization
Show answer

Answer: B. Type 2 (hosted) hypervisors run atop a conventional OS and are common for desktop/dev use instead.

Q3. Kubernetes "self-healing" means:

  1. Failed Pods must be restarted manually
  2. The cluster automatically detects failed Pods and reschedules them to maintain the desired state
  3. Containers repair their own corrupted code
  4. Failures are simply ignored
Show answer

Answer: B. This automated recovery is a major reliability benefit of using an orchestration platform.

Q4. A canary deployment strategy:

  1. Sends 100% of traffic to a new version immediately
  2. Gradually rolls a new version out to a small slice of traffic first, expanding only if it performs well
  3. Deletes the old version before deploying the new one
  4. Requires a full outage during deployment
Show answer

Answer: B. This limits the "blast radius" of a bad release compared to sending it to every user at once.

Q5. Infrastructure as Code (IaC) primarily provides:

  1. Application business logic
  2. Reproducible, version-controlled infrastructure provisioning instead of manual, ad-hoc setup
  3. A replacement for cloud providers
  4. Guaranteed zero infrastructure cost
Show answer

Answer: B. Because it's just config files, IaC can be reviewed, versioned, and reliably rebuilt (e.g. for disaster recovery).
