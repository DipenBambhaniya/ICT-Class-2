CAP Theorem

A distributed database can offer at most two of three guarantees at once: Consistency, Availability, and Partition tolerance. This single idea explains why different NoSQL databases make very different design choices.

The three letters

🧮

C — Consistency

Every read receives the most recent write, or an error. All nodes see the same data at the same time.

🟢

A — Availability

Every request gets a (non-error) response — no guarantee it's the latest data, just that the system responds.

🔌

P — Partition tolerance

The system keeps working even when network communication between nodes breaks down.

The CAP triangle

What each trade-off means in practice

ChoiceSacrificesBehavior during a partitionExample systems
CP — Consistency + Partition toleranceAvailabilityMay reject/delay requests on the affected side rather than return stale dataMongoDB (default), HBase, Redis (with strong config)
AP — Availability + Partition toleranceStrong consistencyKeeps responding on all sides; data converges later (eventual consistency)Cassandra, DynamoDB, CouchDB, Riak
CA — Consistency + AvailabilityPartition toleranceOnly realistic without real network partitions — essentially a single-node systemTraditional single-server RDBMS
Why P is treated as mandatory

In any real distributed system spanning multiple nodes, network partitions will eventually happen. So "CA" is only a theoretical corner — practical distributed NoSQL databases really choose between CP and AP, not whether to support P at all.

Choosing CP vs AP — worked examples

  • Banking / financial ledger → choose CP. An incorrect balance from a stale read is unacceptable, so the system should refuse a request rather than risk it.
  • Global shopping cart / social feed → choose AP. Staying responsive matters more than every replica agreeing instantly; brief staleness is tolerable.
  • Tunable consistency — databases like Cassandra and DynamoDB let you choose consistency strength per operation, blending the trade-off rather than locking into one side globally.
Common exam trap

Don't confuse CAP's "Consistency" with ACID's "Consistency" — CAP is about all replicas agreeing on the same data; ACID is about a transaction obeying integrity constraints. Also remember CAP applies to distributed, multi-node systems — it isn't meaningful for a single, non-networked database.

Quick self-check

  • Can you define C, A, and P in one sentence each?
  • Can you explain why a distributed system can't have all three simultaneously?
  • Can you classify MongoDB and Cassandra correctly as CP vs AP?
