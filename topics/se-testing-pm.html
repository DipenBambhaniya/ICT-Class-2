Software Testing & Project Management

Testing verifies the software works, at increasing scope from unit through acceptance; project management coordinates schedule, budget and risk to actually deliver it. Service Level Agreements (SLAs) tie both together with measurable, contractual commitments.

Key points

Testing levels
Unit (one function) → Integration (modules together) → System (whole app vs requirements) → Acceptance (customer sign-off).
Black-box vs white-box
Black-box tests behavior with no code knowledge; white-box tests internal logic/paths directly; grey-box blends the two.
Defect lifecycle
New → Assigned → In Progress → Fixed → Retested → Closed, tracked through a defect tracking system (e.g., Jira).
Estimation & scheduling
COCOMO estimates effort/cost/schedule; Gantt charts visualize schedule/dependencies; the critical path sets the minimum project duration.
SLA
A formal, measurable service commitment (uptime, response time, defect resolution) with defined consequences if unmet.

Diagram

Example

A payment feature's SLA: "99.9% of payment requests processed successfully
within 2 seconds, measured monthly, with a 10% service credit if missed."

Testing that feature:
  Unit:        test the tax-calculation function with edge-case inputs
  Integration: test that the payment module correctly calls the
               fraud-check module and handles its response
  System:      run a full checkout flow end-to-end against the staging env
  Acceptance:  the client's QA team signs off that checkout matches their
               actual business requirements before go-live

If defect tracking shows a spike in "payment timeout" bugs post-release,
that data feeds back into whether the 2-second SLA target is realistic.
Common exam traps

Defect SEVERITY (technical impact) vs PRIORITY (fix urgency) are related but distinct — frequently swapped. A false positive wrongly reports failure; a false negative wrongly reports success (missing a real bug) — the more dangerous of the two. QA is process-focused/preventive; QC (including testing) is product-focused/detective. Regression testing checks that a CHANGE didn't break EXISTING functionality, not that new functionality works.

Practice MCQs

Q1. Unit testing verifies:

  1. The entire integrated system at once
  2. The smallest individually testable pieces of code (e.g., functions/methods) in isolation
  3. Only the user interface
  4. Only the deployment infrastructure
Show answer

Answer: B. Unit tests isolate the smallest testable units, making failures easy to localize.

Q2. Black-box testing evaluates software by:

  1. Examining internal source code line by line
  2. Testing functionality against inputs and expected outputs without knowledge of the internal code structure/implementation
  3. Only testing the database schema
  4. Requiring full access to the compiled binary's assembly code
Show answer

Answer: B. Black-box testing treats the system as an opaque box, focusing purely on input/output behavior.

Q3. Regression testing is performed to:

  1. Test entirely new, never-before-tested functionality only
  2. Verify that recent code changes haven't broken previously working functionality
  3. Replace the need for any other type of testing
  4. Only run once, at the very start of a project
Show answer

Answer: B. Regression testing guards against previously working features breaking due to new changes.

Q4. An SLA (Service Level Agreement) in a software/IT project context is:

  1. An informal, unwritten understanding with no specifics
  2. A formal agreement specifying measurable service commitments (e.g., uptime, response time, defect resolution time) between a provider and a customer
  3. A type of programming language
  4. Only relevant to hardware manufacturing
Show answer

Answer: B. SLAs formalize measurable service expectations between a provider and its customers.

Q5. Defect severity and defect priority, though related, differ in that severity indicates:

  1. The order/urgency in which a defect should be fixed relative to other work
  2. The technical impact/seriousness of a defect on the system, while priority indicates the order/urgency in which it should be fixed relative to other work
  3. Exactly the same thing as priority, with no distinction
  4. Only the cosmetic appearance of a defect
Show answer

Answer: B. Severity (technical impact) and priority (fix urgency) are related but distinct dimensions of a defect.
