B and B+ Trees

B-trees and B+ trees are balanced, multi-way search trees designed for disk. A high branching factor keeps them only 3–4 levels deep even for millions of keys, so any record is found in a handful of block reads. B+ trees are the default index structure in almost every relational DBMS.

Core properties

Order / fan-out (m)
Maximum number of child pointers in a node. Chosen so one node ≈ one disk block, giving a large m (often 100+).
Balanced
Every leaf is at the same depth. Height ≈ logm(N), so search/insert/delete are all O(log N) block accesses.
Node fill rule
Except the root, every node is at least half full — between ⌈m/2⌉ and m children. This bounds wasted space and keeps height low.
Split & merge
Insert into a full node → split and push the middle key up. Delete below half full → borrow from a sibling or merge.

B-tree vs B+ tree

AspectB-treeB+ tree
Where data/record pointers liveIn every node (internal + leaf)In the leaf nodes only
Internal nodes holdKeys + data pointers + child pointersKeys + child pointers only (routing)
Key duplicationEach key appears once in the whole treeSeparator keys are copied up; every key also appears in a leaf
Leaf linkageLeaves not linkedLeaves form a linked list → fast range scans & full-index scan
Fan-outLower (internal nodes carry data)Higher → shorter tree
Search costCan stop early at an internal nodeAlways traverses to a leaf (predictable)

Start leaf:      [ 11 , 15 ]           parent: | 20 |
Insert 13  ->    [ 11 , 13 , 15 ]      overflow (3 > 2)  -> SPLIT
Split:           [ 11 ]   [ 13 , 15 ]  push copy of 13 up
Parent becomes:  | 13 | 20 |

Height only grows when the ROOT splits — that is why a B+ tree
stays balanced and shallow.
Common exam traps

In a B+ tree the actual data / record pointers are in the leaves only; internal nodes are pure routing. Both trees are always height-balanced — an insertion never makes one path longer than another. A B-tree can find a key at an internal node and stop early; a B+ tree always descends to a leaf. B+ trees beat B-trees for range queries because of the linked leaf list.

Practice MCQs

Q1. In a B+ tree, record (data) pointers are stored in:

  1. The root node only
  2. All internal nodes
  3. The leaf nodes only
  4. A separate overflow area
Show answer

Answer: C. B+ tree internal nodes hold only separator keys and child pointers; every actual key with its data pointer sits in a leaf, and the leaves are linked for sequential access.

Q2. The main reason B+ trees are preferred over B-trees for database indexes handling range queries is:

  1. They use less disk space always
  2. Their leaf nodes are linked in a sorted list, enabling efficient sequential/range scans
  3. They are not height-balanced
  4. They store no keys in internal nodes
Show answer

Answer: B. After locating the start of a range at a leaf, the DBMS follows the leaf-level linked list to read all qualifying keys in order without revisiting internal nodes.

Q3. In a B-tree of order m, every non-root internal node has at least how many children?

  1. 1
  2. 2
  3. ⌈m/2⌉
  4. m
Show answer

Answer: C — ⌈m/2⌉. The half-full rule guarantees at least ⌈m/2⌉ children (⌈m/2⌉−1 keys) in every node except the root, which keeps the tree height ≈ logmN.

Q4. When a key is inserted into a B+ tree leaf that is already full, the DBMS:

  1. Rejects the insertion
  2. Splits the node and propagates a separator key to the parent
  3. Converts the leaf into an internal node
  4. Stores the key in the root
Show answer

Answer: B. The overfull node splits into two half-full nodes and a copy of the middle key is inserted into the parent; splits cascade upward only if the parent is also full.

Q5. The height of a B+ tree holding N keys with node fan-out f is approximately:

  1. N / f
  2. √N
  3. logf N
  4. f · log N
Show answer

Answer: C — logf N. Each level multiplies capacity by the fan-out, so a large f (many keys per block) keeps a multi-million-row index just 3–4 levels — hence 3–4 block reads per lookup.

Q6. Which statement about B-trees is FALSE?

  1. All leaf nodes are at the same level
  2. A search key may appear in an internal node
  3. The tree can become unbalanced after many insertions
  4. It is designed to minimise disk block accesses
Show answer

Answer: C. B-trees stay perfectly height-balanced by construction — splits and merges keep every leaf at the same depth no matter the insertion order.
