SCADA & Software Quality

SCADA systems supervise and control real physical infrastructure — power grids, water treatment, manufacturing — where a software failure has real-world consequences. That elevated stakes makes formal software quality models (ISO/IEC 25010, CMMI) and disciplined technical-debt management especially important.

Key points

SCADA architecture
Field devices (RTU/PLC) collect data and relay commands ↔ telemetry network ↔ MTU/central server ↔ HMI dashboard for human operators.
SCADA security
Legacy protocols, historically air-gapped but now often network-connected — a successful attack can disrupt real physical infrastructure, not just data.
ISO/IEC 25010
Eight quality characteristics: functional suitability, reliability, performance efficiency, usability, security, compatibility, maintainability, portability.
CMMI maturity levels
Initial (ad hoc) → Managed → Defined (org-wide standard) → Quantitatively Managed → Optimizing (continuous, data-driven improvement).
Technical debt
The future rework cost of a quick-and-easy shortcut taken now; a strong test suite makes later refactoring to pay it down safer.

Example

A water-treatment plant's SCADA system:
  - PLCs at each pump station monitor flow rate and chlorine levels
  - RTUs relay this data over the telemetry network to the central MTU
  - The MTU aggregates readings; the HMI shows operators a live dashboard
    with an ALARM if chlorine drops below a safe threshold

Quality strategy for this system, given the real-world safety stakes:
  - Reliability & Security (ISO/IEC 25010) are prioritized above all else
  - The vendor's development process is assessed against CMMI to confirm
    disciplined, repeatable engineering practices
  - Network segmentation (not just an old air-gap assumption) protects
    the telemetry network from external compromise
Common exam traps

SCADA's RTU (field-level, near the sensors) vs MTU (central, supervisory) are often swapped. Air-gapping was the classic SCADA security approach, but modern practice favors network segmentation + monitoring since full isolation is often no longer practical. CMMI's 'Managed' level still means largely per-project, reactive processes — 'Defined' is where practices become standardized organization-wide.

Practice MCQs

Q1. SCADA stands for:

  1. Software Configuration And Data Analysis
  2. Supervisory Control and Data Acquisition, a system architecture used to monitor and control industrial processes
  3. Secure Cloud Application Deployment Architecture
  4. Standard Control And Design Automation
Show answer

Answer: B. SCADA systems are widely used to monitor/control industrial and infrastructure processes remotely.

Q2. An RTU (Remote Terminal Unit) in a SCADA system is responsible for:

  1. Only displaying the operator dashboard
  2. Collecting data from field sensors/equipment and transmitting it to the central monitoring system, and relaying control commands back to field devices
  3. Only billing customers for electricity usage
  4. Only compiling application source code
Show answer

Answer: B. RTUs are the field-level data collection and control-relay points in a SCADA architecture.

Q3. The ISO/IEC 25010 software quality model defines quality in terms of characteristics such as:

  1. Only the color scheme of the software
  2. Functional suitability, reliability, performance efficiency, usability, security, compatibility, maintainability, and portability
  3. Only the programming language used
  4. Only the marketing budget allocated
Show answer

Answer: B. ISO/IEC 25010 defines a comprehensive, multi-dimensional model of software product quality.

Q4. CMMI's maturity levels progress (from least to most mature) roughly as:

  1. Optimizing, Defined, Managed, Initial, Quantitatively Managed
  2. Initial, Managed, Defined, Quantitatively Managed, Optimizing
  3. Managed, Initial, Optimizing, Defined, Quantitatively Managed
  4. There is only a single CMMI maturity level
Show answer

Answer: B. This is the standard CMMI staged representation, from ad hoc (Initial) to continuously improving (Optimizing).

Q5. Technical debt, as a software quality concept, refers to:

  1. The literal monetary loan a company takes to fund development
  2. The implied future cost of additional rework caused by choosing an easy/quick solution now instead of a better, more thorough approach
  3. A metric measuring how many developers are on the team
  4. The total number of servers a company operates
Show answer

Answer: B. Technical debt is a metaphor for the future cost of taking shortcuts in the present.
