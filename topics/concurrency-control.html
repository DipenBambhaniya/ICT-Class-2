Concurrency Control

Concurrency-control protocols decide how to interleave the operations of simultaneous transactions so that the resulting schedule is always serializable and recoverable — without giving up too much throughput.

Lock-based protocols

Transactions must acquire a lock before accessing a data item. Two lock modes:

Requested ↓ / Held →NoneShared (S)Exclusive (X)
Shared (S) — for read✔ grant✔ grant✘ wait
Exclusive (X) — for write✔ grant✘ wait✘ wait
Two-Phase Locking (2PL)
Each transaction has a growing phase (only acquires locks) followed by a shrinking phase (only releases locks). Once it releases any lock it can never acquire another. 2PL guarantees conflict-serializable schedules.
Strict 2PL
All exclusive locks held until commit/abort → cascadeless + recoverable. Most common in practice.
Rigorous 2PL
All locks (S and X) held until commit → serialization order = commit order.
Downside
2PL can cause deadlock and starvation; it does not by itself prevent deadlock.

Other protocol families

Timestamp Ordering (TO)
Each transaction gets a unique timestamp TS. Conflicting operations must execute in timestamp order; a transaction that arrives "too late" is aborted and restarted with a new TS. No deadlock, but possible starvation and cascading rollback. The Thomas write rule ignores obsolete writes.
Multiversion / MVCC (snapshot isolation)
Writers create a new version instead of overwriting; readers see a consistent snapshot and never block writers. Used by PostgreSQL, Oracle, MySQL InnoDB.
Optimistic (validation-based)
Three phases: read (work on private copies), validation (check for conflicts at commit), write (apply if valid, else abort). Best when conflicts are rare.

Deadlock handling

ApproachHow it works
Prevention — Wait-DieOlder waits for younger; younger requesting an older's lock is aborted ("dies"). Non-preemptive.
Prevention — Wound-WaitOlder requesting a younger's lock preempts ("wounds") it; younger waits for older. Preemptive.
DetectionMaintain a wait-for graph; a cycle = deadlock → abort a victim transaction.
TimeoutAbort any transaction that waits longer than a threshold. Simple but may kill non-deadlocked transactions.

Example — 2PL schedule

T1:  lock-X(A)  read(A)  A:=A-50  write(A)  lock-X(B) ... unlock(A) ...
T2:  lock-S(A)                    -- BLOCKED: T1 holds X on A
     ... waits until T1 reaches its shrinking phase and unlocks A ...

Growing phase of T1 : all lock-X(...) acquired, none released
Lock point          : just before the first unlock
Shrinking phase     : unlock(A), unlock(B)   -- no new locks allowed here
Common exam traps

Basic 2PL ensures serializability but not freedom from deadlock, and not cascadelessness — you need strict 2PL for that. Timestamp ordering is deadlock-free (it aborts instead of waiting). Two-phase locking (2PL) is unrelated to the two-phase commit (2PC) protocol used for distributed atomicity.

Practice MCQs

Q1. The two-phase locking protocol guarantees:

  1. Freedom from deadlock
  2. Conflict-serializable schedules
  3. Cascadeless schedules always
  4. Maximum concurrency
Show answer

Answer: B. 2PL's growing-then-shrinking discipline is sufficient to guarantee conflict serializability, but it can still deadlock, and only strict 2PL guarantees cascadelessness.

Q2. Under 2PL, once a transaction releases its first lock it:

  1. Must immediately commit
  2. Cannot acquire any new locks
  3. Can still acquire shared locks but not exclusive locks
  4. Enters the growing phase
Show answer

Answer: B. The first unlock marks the transition to the shrinking phase; from then on the transaction may only release locks, never request new ones.

Q3. Which concurrency-control method is inherently free of deadlock?

  1. Two-phase locking
  2. Strict two-phase locking
  3. Timestamp ordering protocol
  4. Graph-based locking with shared locks
Show answer

Answer: C. Timestamp ordering never makes a transaction wait for a lock — a conflicting late operation is simply aborted and restarted — so no wait-for cycle can form.

Q4. In the wait-die deadlock-prevention scheme, when an older transaction requests an item locked by a younger one:

  1. The older transaction is aborted
  2. The older transaction waits
  3. The younger transaction is aborted
  4. Both transactions are aborted
Show answer

Answer: B. In wait-die, an older (higher-priority) transaction is allowed to wait for a younger one; only a younger transaction requesting an older one's lock is rolled back ("dies").

Q5. A shared (S) lock held by T1 on item Q is compatible with:

  1. An exclusive lock request by T2 on Q
  2. A shared lock request by T2 on Q
  3. Both shared and exclusive requests by T2
  4. No other lock request
Show answer

Answer: B. Multiple transactions may hold shared (read) locks simultaneously; an exclusive (write) lock requires that no other lock of any kind is held.

Q6. Optimistic concurrency control performs conflict checking during which phase?

  1. Read phase
  2. Validation phase
  3. Write phase
  4. Commit-log phase
Show answer

Answer: B — Validation phase. The transaction works on private copies during the read phase, then at commit time the validation phase checks whether its read/write set conflicts with recently committed transactions; if so it aborts and restarts.
