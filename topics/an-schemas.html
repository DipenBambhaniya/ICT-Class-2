Star / Snowflake / Fact Constellation Schemas

Three dimensional modeling patterns for organizing a data warehouse: the simple, denormalized star; the normalized, storage-efficient snowflake; and the multi-fact-table constellation for related business processes.

Key points

Star schema
One central fact table joined directly to denormalized dimension tables. Fewest joins, fastest typical queries, some redundancy.
Snowflake schema
Dimension tables normalized into related sub-tables (e.g. Product → Subcategory → Category). Less redundancy, but more joins needed.
Fact constellation (galaxy schema)
Multiple fact tables (different business processes, e.g. Sales and Shipping) sharing conformed dimensions for integrated analysis.
Conformed dimension
A dimension (like Time or Product) designed consistently and shared across multiple fact tables — what makes a fact constellation work.
Degenerate & junk dimensions
Degenerate: an identifier (like an order number) kept directly in the fact table with no separate dimension table. Junk: bundles several small unrelated flags into one dimension table.

Diagram

Example

Star (denormalized Product dimension):
  dim_product: product_id, name, subcategory, category, department
  -- one flat table, some repeated category/department text

Snowflake (normalized):
  dim_product: product_id, name, subcategory_id
  dim_subcategory: subcategory_id, name, category_id
  dim_category: category_id, name, department_id
  -- less redundancy, but 3 joins instead of 1 to get full context

Fact Constellation:
  fact_sales(product_id, store_id, time_id, amount)
  fact_shipments(product_id, warehouse_id, time_id, qty)
  -- both share dim_product and dim_time (conformed dimensions)
Common exam traps

Star = denormalized, fewer joins, faster typical queries. Snowflake = normalized, more joins, less storage redundancy. Fact constellation = MULTIPLE fact tables sharing conformed dimensions — not just a bigger star. A conformed dimension must be defined consistently everywhere it's shared, or cross-process analysis breaks.

Practice MCQs

Q1. A star schema consists of:

  1. Only dimension tables with no fact table
  2. A central fact table connected directly to denormalized dimension tables
  3. Multiple fact tables with no dimensions
  4. A single fully normalized table
Show answer

Answer: B. Visually resembles a star.

Q2. A snowflake schema differs from a star schema by:

  1. Having no dimension tables
  2. Normalizing dimension tables into related sub-tables
  3. Never having a fact table
  4. Being identical to a star schema
Show answer

Answer: B. Reduces redundancy at the cost of more joins.

Q3. A fact constellation (galaxy) schema is characterized by:

  1. Exactly one fact table
  2. Multiple fact tables sharing conformed dimensions
  3. No fact tables at all
  4. Being identical to a simple star schema
Show answer

Answer: B. Useful for multiple related business processes.

Q4. The main trade-off between star and snowflake schemas is:

  1. Star is always slower and uses more storage
  2. Star reduces joins/query complexity at the cost of redundancy; snowflake reduces redundancy at the cost of more joins
  3. There is no meaningful trade-off
  4. Snowflake never uses any joins
Show answer

Answer: B. The classic star-vs-snowflake trade-off.

Q5. A conformed dimension is:

  1. Used by only one fact table, never shared
  2. Designed consistently and shared across multiple fact tables
  3. A synonym for the fact table
  4. Unrelated to fact constellations
Show answer

Answer: B. Exactly what makes a fact constellation's multiple fact tables analytically compatible.
