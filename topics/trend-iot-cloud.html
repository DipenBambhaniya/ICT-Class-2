IoT, Big Data & Cloud-Native Computing

The Internet of Things (IoT) connects physical sensors and devices — in smart cities, agriculture and industry — that continuously generate large, fast-moving, varied streams of data, the "Big Data" challenge captured by the 5 Vs. Cloud-native computing (containers, microservices, Kubernetes, serverless) provides the elastic infrastructure to store and process that data at scale, while edge computing pushes some processing closer to the data source to cut latency.

Key points

IoT architecture
Sensors/devices (sense the physical world) → connectivity/gateway (transmit data, e.g., via Wi-Fi, cellular, LPWAN) → cloud/platform (scalable storage & analytics) → application layer (dashboards, alerts, automated actions for end users).
Example IoT use cases
Smart cities (traffic/air-quality sensors), precision agriculture (soil-moisture sensors optimising irrigation), and Industrial IoT (machine sensors enabling predictive maintenance).
Big Data's 5 Vs
Volume (scale of data), Velocity (speed of generation/processing), Variety (structured/semi-structured/unstructured formats), Veracity (trustworthiness/quality), Value (the actual usefulness extracted through analysis).
Cloud-native computing
Containers package an app with its dependencies (lighter than a full VM); microservices break an app into small, independently deployable services; Kubernetes/orchestration automates deploying, scaling and healing containers; serverless (FaaS) runs event-triggered code without managing servers directly.
Edge computing
Processes data closer to its source (near the device/sensor) to reduce latency and bandwidth use, complementing — not replacing — centralised cloud processing for large-scale analytics.

Diagram

Example

A smart-city traffic management deployment:
  1. Thousands of IoT sensors at intersections continuously report traffic
     flow and air-quality readings (high VOLUME, high VELOCITY, mixed
     VARIETY of sensor data types)
  2. A local edge gateway at each intersection processes readings
     immediately to adjust signal timing in real time (low latency,
     avoiding a slow round trip to a distant data centre)
  3. Aggregated data is streamed to a cloud-native analytics platform --
     built from containerised microservices, auto-scaled by an
     orchestrator like Kubernetes as sensor volume grows -- to detect
     city-wide congestion trends over weeks and months
  4. A city-operations dashboard (application layer) shows live traffic
     status to traffic-control staff and citizens

Big Data lens: VOLUME (many sensors), VELOCITY (real-time streams),
VARIETY (traffic counts + air-quality readings), VERACITY (sensor
calibration/quality checks), VALUE (actually improving traffic flow)
Common exam traps

Don't confuse edge computing with cloud computing — edge processes data near the source for low latency; cloud handles large-scale storage/analytics centrally; in practice they're complementary, not either/or. A container is NOT a full virtual machine — containers share the host OS kernel (lightweight), while a VM includes its own full guest OS (heavier). Serverless computing does not mean "no servers exist" — it means the developer doesn't manage them directly. Remember all 5 Vs of Big Data (Volume, Velocity, Variety, Veracity, Value) — exams often test whether you can match a scenario to the right "V".

Practice MCQs

Q1. The 'Veracity' aspect of Big Data's '5 Vs' framework refers to:

  1. The trustworthiness, accuracy, and quality of the data, since noisy, incomplete, or inconsistent data can undermine the reliability of any analysis built on it
  2. The sheer volume of data collected
  3. The number of different data formats present
  4. How quickly new data arrives
Show answer

Answer: A. Veracity is about data quality and trustworthiness — an essential consideration since flawed input data leads to flawed analytical conclusions ("garbage in, garbage out").

Q2. A 'microservices' architecture structures an application as:

  1. A single, large, tightly-coupled program where every feature is bundled inseparably together (a 'monolith')
  2. A collection of small, independently deployable services, each responsible for a specific business capability, that communicate with each other typically over network APIs
  3. A design with no separation of functionality whatsoever
  4. An architecture that can only ever run on a single physical server
Show answer

Answer: B. Microservices break an application into small, independently deployable, loosely-coupled services — a contrast to a traditional monolithic application design.

Q3. Kubernetes, conceptually, is best described as an example of:

  1. A single physical server sold by one specific hardware vendor
  2. A programming language used to write application business logic
  3. A type of database management system with no relation to containers
  4. A container orchestration platform that automates the deployment, scaling, networking, and management of containerised applications across a cluster of machines
Show answer

Answer: D. Kubernetes automates the operational aspects of running many containers at scale — deployment, scaling, networking, and self-healing — across a cluster.

Q4. A key motivation for using edge computing instead of relying solely on centralised cloud processing is:

  1. Edge computing always increases latency compared to centralised cloud processing with no exception
  2. Edge computing eliminates the need for any cloud infrastructure to exist anywhere
  3. Reducing latency (response time) and bandwidth usage by processing time-sensitive data locally, near its source, rather than sending everything to a distant data centre and waiting for a response
  4. Edge computing requires sending every byte of raw data to the cloud before any processing can occur
Show answer

Answer: C. Local processing near the data source can dramatically cut the round-trip delay and network load involved in sending everything to a centralised cloud, which matters for latency-sensitive applications.

Q5. Serverless computing is best described as a cloud computing model in which:

  1. Applications run with absolutely no computer hardware or servers involved anywhere in the world
  2. Developers must personally configure and maintain every physical server themselves
  3. A synonym for traditional on-premises hosting with no cloud involvement
  4. Developers write and deploy code without having to manage the underlying servers directly — the cloud provider automatically provisions, scales, and manages the infrastructure needed to run that code on demand
Show answer

Answer: D. 'Serverless' means the developer is abstracted away from server management — the provider handles provisioning and scaling automatically, even though physical servers still exist somewhere.
