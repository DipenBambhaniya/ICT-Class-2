NoSQL Data Types & Representation

"NoSQL" is not one data model — it's an umbrella term for four distinct families, each representing data differently and suited to different problems.

The four NoSQL families

Model-by-model summary

ModelUnit of storageExamplesBest-fit use case
Key-ValueA key mapped to an opaque value/blobRedis, DynamoDB, RiakCaching, session storage, fast single-key lookups
DocumentA self-contained JSON/BSON documentMongoDB, CouchDB, FirestoreUser profiles, product catalogs, CMS content
Column-familyRows identified by key, columns grouped into familiesCassandra, HBaseTime-series data, write-heavy, huge sparse datasets
GraphNodes (entities) and edges (relationships), both with propertiesNeo4j, ArangoDB, Amazon NeptuneSocial networks, recommendations, fraud detection

Representation formats you should recognize

  • JSON — human-readable text format; the default representation for most document databases.
  • BSON — MongoDB's binary-encoded superset of JSON; adds types like dates and binary data, and is faster to parse.
  • Wide-column — rows can have different columns; column families group related columns for efficient reads.
  • Property graph — the standard graph representation: labeled nodes and labeled, directed edges, each with key-value properties.
Common exam trap

Watch for matching-style questions pairing a model to the wrong example (e.g., "Graph → Cassandra" is wrong; Cassandra is column-family). Memorize one flagship example per model: Key-Value → Redis, Document → MongoDB, Column-family → Cassandra, Graph → Neo4j.

Quick self-check

  • Can you match all four models to a flagship database?
  • Can you pick the right model given a use-case description (e.g., "shortest path between friends")?
  • Do you know why document stores avoid multi-table JOINs?
